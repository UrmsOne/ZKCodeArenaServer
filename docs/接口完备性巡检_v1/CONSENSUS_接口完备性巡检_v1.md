## 需求共识
- `pkg/app/api-server/server` 下所有 REST API 必须覆盖 `docs/v1.0需求/v1.0需求文档.md`
- 每个接口需明确：HTTP 方法、URL、权限要求、请求/响应结构、错误码
- 如发现需求与实现冲突，需同步反馈并调整

## 验收标准
1. 接口覆盖清单：列出所有接口并标记与需求项的映射关系
2. 权限校验：每个接口的角色/身份验证逻辑符合需求约束
3. 响应结构：返回字段、错误处理符合业务约定（参考 `pkg/utils/response.go`）
4. Swagger 文档：可通过浏览器访问并涵盖全部接口说明
5. 自动化测试：关键流程具备链路级单元/集成测试，并在开发环境通过

## 技术方案
- **Swagger 集成**：引入 `github.com/swaggo/swag`、`github.com/swaggo/gin-swagger`，通过注释生成 OpenAPI 文档
- **接口自检**：对 `server` 层 handler 与 service 层进行联合核查，补齐缺失校验
- **测试策略**：使用 `net/http/httptest` + gin 上下文模拟，必要时对 service 层使用 mock；部分链路可走实际 service 实现以验证权限逻辑
- **数据依赖**：测试中避免真实 Mongo/Redis（首选 mock 或内存实现），如需真实依赖则准备测试配置与清理脚本

## 任务边界
- 不新增超出 v1.0 需求的功能
- 不改动服务核心架构，仅补齐校验、响应、一致性问题
- 文档生成限于后端（前端 mock/SDK 不在本次范围）

## 风险与应对
- 需求文档若与现有实现存在差异 → 及时记录并请示处理
- Swagger 集成可能要求大量注释 → 采用阶段性迭代，优先核心接口
- 测试环境缺数据 → 编写测试夹具或使用 mock 数据
