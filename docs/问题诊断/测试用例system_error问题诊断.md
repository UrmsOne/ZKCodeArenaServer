# 测试用例system_error问题诊断指南

## 问题描述

提交代码后返回 `system_error`，但运行接口能成功。测试用例的输入和输出都是"测试用例1"。

## 诊断逻辑

### 判断流程

```
测试用例运行
  ↓
1. 读取测试用例数据
   ├─ 如果Input/Output是占位符（如"测试用例1"）→ 数据读取/存储问题
   └─ 如果Input/Output正常 → 继续
  ↓
2. 沙箱运行代码
   ├─ 返回 Accepted → 进入输出比对
   │   ├─ 输出匹配 → accepted
   │   └─ 输出不匹配 → wrong_answer
   │
   ├─ 返回 SystemError → system_error ⚠️
   │   └─ 这是导致system_error的直接原因
   │
   └─ 返回其他状态 → time_limit/memory_limit/runtime_error
```

### 关键判断点

#### 情况1：数据读取失败（占位符数据）

**症状**：
- 日志中出现：`⚠️ 检测到测试用例可能使用占位符数据`
- Input = "测试用例1"
- Output = "测试用例1"

**原因**：
- 测试用例在创建时使用了占位符数据
- 数据库中的数据本身就是占位符

**解决方法**：
1. 检查数据库中该测试用例的实际数据
2. 如果是占位符，需要更新为正确的输入输出数据
3. 验证测试用例创建流程，确保不允许占位符数据

#### 情况2：沙箱运行失败（运行错误）

**症状**：
- 日志中出现：`测试用例返回系统错误: TestCaseID=xxx, ExitCode=xxx, Error=xxx`
- 或：`未知的运行状态: Status=xxx`

**原因**：
- 沙箱运行时发生了系统级错误
- 可能是：程序异常退出、资源限制、沙箱环境问题

**解决方法**：
1. 查看日志中的 `ExitCode` 和 `Error` 信息
2. 检查代码是否有语法错误、逻辑错误
3. 检查沙箱服务是否正常运行
4. 对比运行接口（只运行示例用例）和提交接口（运行所有用例）的区别

#### 情况3：输出比对失败（应该是wrong_answer，不是system_error）

**症状**：
- 日志中出现：`输出不匹配: TestCaseID=xxx, 期望输出=xxx, 实际输出=xxx`
- 沙箱返回 `Accepted`，但输出比对失败

**原因**：
- 代码逻辑错误，输出不正确
- 但这应该返回 `wrong_answer`，不会导致 `system_error`

## 问题排查步骤

### 步骤1：查看日志中的占位符警告

查看服务器日志，搜索：
```
检测到测试用例可能使用占位符数据
```

如果出现此警告：
- ✅ **确认**：是数据读取/存储问题
- ✅ **解决**：更新数据库中的测试用例数据

### 步骤2：查看沙箱运行状态

查看日志中的：
```
测试用例返回系统错误
```
或
```
未知的运行状态
```

关注信息：
- `Status`: 沙箱返回的状态值
- `ExitCode`: 程序退出码（非0通常表示错误）
- `Error`: 错误信息（stderr输出）

### 步骤3：对比运行接口和提交接口

**运行接口** (`/run`)：
- 只运行示例测试用例（`IsSample = true`）
- 如果示例用例都能通过，说明代码基本逻辑正确

**提交接口** (`/submit`)：
- 运行所有测试用例（包括隐藏的非示例用例）
- 如果某个隐藏用例导致system_error，需要检查该用例的特殊性

### 步骤4：检查测试用例数据

直接查询数据库：
```javascript
// MongoDB查询
db.test_cases.find({
  problem_id: ObjectId("68fde18e10edcace62ce5f64")
})
```

检查每个测试用例的：
- `input`: 输入数据是否正确
- `output`: 期望输出是否正确
- `is_sample`: 是否为示例用例

## 常见问题场景

### 场景1：占位符数据导致的问题

**问题**：
- 测试用例创建时使用了"测试用例1"作为占位符
- 提交接口运行时，代码接收输入"测试用例1"
- 但程序可能无法处理这种输入，导致运行时错误

**解决**：
- 更新测试用例，使用真实的测试数据

### 场景2：隐藏测试用例的特殊要求

**问题**：
- 示例测试用例很简单，能通过
- 隐藏测试用例可能：
  - 输入数据更大
  - 边界条件更严格
  - 时间/内存限制更紧

**解决**：
- 查看日志中具体是哪个测试用例失败
- 分析该测试用例的特殊性
- 优化代码以处理该用例

### 场景3：代码无法处理某些输入

**问题**：
- 代码逻辑有bug，无法正确处理某些输入
- 导致程序异常退出（非0退出码）
- 沙箱返回SystemError

**解决**：
- 查看日志中的 `ExitCode` 和 `Error`
- 修复代码逻辑错误
- 添加异常处理

## 总结

### 快速判断方法

1. **查看日志中的占位符警告** → 数据问题
2. **查看沙箱返回的状态**：
   - `Status = "System Error"` → 运行失败
   - `Status = "Accepted"` 但输出不匹配 → 逻辑错误（应该返回wrong_answer）
   - `Status = 未知值` → 状态解析问题
3. **查看ExitCode**：
   - `ExitCode != 0` → 程序异常退出
   - `ExitCode = 0` 但Status不对 → 状态判断问题

### 代码改进后的优势

现在的代码会在日志中明确显示：
- ✅ 测试用例的输入输出内容（前50字符预览）
- ✅ 是否检测到占位符数据
- ✅ 沙箱返回的详细状态信息
- ✅ 输出比对结果（如果进入比对流程）

这些信息可以快速定位是**数据读取问题**还是**运行失败问题**。
