# ALIGNMENT - 每日一题与题目统计功能

## 原始需求

用户提出了以下4个具体需求：
1. **开发每日一题功能** - 传递题目信息到前端
2. **提供题库的简单题/中等题/困难题等数量的功能**
3. **分析GetProblems和SearchProblems这两个接口的返回参数**
4. **对目前problem和testcase代码质量做出评估，有什么可以优化的**

## 项目上下文分析

### 🏗 现有架构分析

#### 技术栈
- **后端框架**: Go + Gin
- **数据库**: MongoDB
- **认证**: JWT
- **文档**: Swagger
- **架构模式**: 分层架构 (Server → Service → Database)

#### 现有题目相关功能
1. **题目管理**: 完整的CRUD操作
2. **题目列表**: `GetProblems` - 支持分页、难度筛选、标签筛选、用户状态显示
3. **题目搜索**: `SearchProblems` - 支持关键词搜索
4. **题目详情**: `GetProblem` - 获取完整题目信息
5. **代码运行**: `RunCode` - 支持代码测试

#### 现有统计功能
1. **系统统计** (`StatisticsService.GetSystemStatistics`):
   - 题目总数、用户总数、提交总数
   - **各难度题目分布** (`DifficultyDistribution`) ✅ 已实现
   - 最近24小时活跃度统计

2. **用户统计** (`StatisticsService.GetUserStatistics`):
   - 个人AC率、尝试题目数、通过题目数
   - 各难度通过统计

#### 数据模型
- **Problem**: 完整题目信息，包含难度枚举 (easy/medium/hard)
- **ProblemList**: 题目列表项，包含用户状态
- **ProblemDifficulty**: 三级难度分类
- **UserProblemStatus**: 用户题目状态 (未尝试/已尝试/已通过)

## 疑问澄清

### 🤔 每日一题推荐策略
**问题**: 每日一题的推荐逻辑具体要求？
**选项**:
1. **简单随机**: 从所有已发布题目中随机选择
2. **难度递进**: 根据用户能力逐步提升难度
3. **标签轮换**: 按标签分类轮换推荐
4. **个性化推荐**: 基于用户历史记录推荐

### 🤔 每日一题的持久化
**问题**: 每日一题是否需要持久化存储？
**选项**:
1. **实时计算**: 每次请求时计算当日推荐
2. **每日缓存**: 每天生成并缓存当日推荐
3. **历史记录**: 保存历史推荐记录

### 🤔 难度统计API的需求
**问题**: 是否需要独立的轻量级难度统计API？
**考虑**: 现有`GetSystemStatistics`返回数据较多，前端可能只需要难度分布

## 技术约束和集成方案

### 集成约束
- **保持现有架构**: 遵循Server→Service→Database分层
- **复用现有组件**: 使用现有的认证、权限、数据模型
- **向后兼容**: 不影响现有功能和接口
- **数据库优化**: 避免影响现有查询性能

### 技术选型
- **缓存策略**: 使用内存缓存存储每日推荐（可选Redis）
- **推荐算法**: 基于简单随机+难度权重的策略
- **API设计**: RESTful风格，与现有接口保持一致
- **错误处理**: 使用项目现有的utils.ErrorResponse体系
